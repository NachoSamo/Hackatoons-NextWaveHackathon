The pipeline

Five layers, one direction of flow

Data enters on the left and leaves on the right as an actionable diagnosis. The rule that orders everything: deterministic code computes and decides; the AI only communicates. Detection, localization, classification and action selection are auditable, reproducible code. The language model phrases the result for two audiences and answers questions about it — it never produces a number and never changes a verdict.

Layer by layer

What each one does — and what it does not

0

Traffic generator

synthetic stream · replay + injection
Implemented
Does
Produces credible synthetic transactions (merchant, provider, method, country, approved y/n, decline code, amount). A deterministic history with a diurnal and weekday profile is pre-generated and replayed at 65 tx/s. A separate injector overlays incidents by degrading approval probability for a chosen dimensional slice.
Does not
It does not generate live, so the detector can be calibrated against the same data that is displayed. The injector never inserts fabricated declines: it shifts probabilities and lets the world respond.
Stack
Python · pandas · seeded replay · parametric injector with scope, magnitude and duration.
Storage
Ring buffer (in memory, 30 min) is the hot path: 60-second cube, evidence, money. Parquet holds the static artifacts: baseline_profile (14-day contextual forecast) and the healthy fixture the replayer loops. PostgreSQL is optional, a cold transaction archive for auditability — nothing on the hot path depends on it.
Verification
The world is reproducible from its seed: regenerating the baseline and the fixture yields byte-identical artifacts, so any detection result can be replayed exactly.
1

Deterministic engine — Detector → Localizer

the core · no LLM
Implemented
Detector
Models the expected hourly conversion and runs a one-sided binomial CUSUM over the residual, per slice. Working from successes and attempts rather than the ratio folds volume into the decision: a drop across 5 attempts and a drop across 500 stop being treated alike. This filters diurnal noise, weekends and ordinary variance.
Localizer
For each candidate slice it simulates the ripple effect — if this were the cause, how would the rest of the cube look? — compares that against what was observed and keeps the smallest explanation that best covers it.
Simultaneous causes
Multiplicative residualization: once a cause wins, its ripple is discounted from both the deficit and the still-available baseline before searching again. This separates two concurrent incidents even when they share a country and cube leaves, without turning issuer or decline code into dimensions.
Classifier
A separate deterministic module combines slice + decline_shift + issuer evidence + confidence into diagnosis_category (provider_degradation, issuer_unavailable, …). A plain response-code lookup would not be enough: the same code means different causes depending on the shape of the slice and which control segments stay healthy.
Does not
No language model. No action execution. No invention: when the sample is small and the Wilson interval wide, it marks diagnosis_status ≠ supported and the system recommends monitoring instead of an intervention.
Stack
Pure Python · pandas/numpy. Conceptual basis: Squeeze / HotSpot.
Verification
An acceptance runner replays 90 healthy windows with no incident and requires additional persistence for weak, low-volume slices. Scenarios cover healthy silence, concurrent incidents, overlap, recovery and a dimensional combination never used during development.
2

Explanation layer — Communication

business rules in .md · static
Implemented
Does
Receives the structured output from the engine, the action already selected from the catalog, the evidence and the cost. It loads the payment business rules held as .md files and uses a language model, without tools, only to write for two audiences: an executive line and an operational readout.
Does not
It does not look for the root cause, compute anything or choose the action. All of that arrives already resolved and auditable. The rule base is static at runtime.
Copilot
The second surface of the model: it answers operator questions about an already-resolved diagnosis. It shares the same rule base used to write that diagnosis, so it cannot contradict on screen what the same rules already produced. It cannot change the diagnosis or the action, and when a question exceeds the evidence bundle it says so instead of inventing an answer. The interface renders a deterministic answer immediately and replaces it only if the model responds in time.
Stack
Pydantic AI (OpenAI, no tools) + .md rule files · schema-validated output · temperature 0.
Verification
Every path runs without an API key: deterministic Jinja templates render the same evidence, the same cost and the same action, so wording quality degrades but operational truth does not. A self-check exercises the three reference incidents offline.
3

Playbook + Templates

from diagnosis to a next action
Implemented
Action
Selected deterministically from a YAML catalog keyed by diagnosis_category, with one entry per category plus a monitor entry for insufficient evidence. Each carries the likely owner, the parameters to change, the expected impact and a re-evaluation window.
Evidence + headline
Readable bullets built from the decline shift, issuer evidence and reason codes. The headline is a template carrying the situation, the slice and the money at risk — the model does not write it, so the figure on screen always comes from the cost calculation.
Cost
Derived from the data layer: average ticket for the affected cells against the baseline, extrapolated hourly. When that layer is unavailable it falls back to a fixed ticket and states the assumption explicitly in the output.
Does not
It does not execute the action. Every recommendation carries simulation_only: true.
Stack
YAML catalog + Jinja templates. No language model in this layer.
Verification
Each supported category of the deterministic taxonomy resolves to a distinct catalog action, and an insufficient-evidence incident resolves to monitoring with no cost figure attached.
4

Delivery — Dashboard + channel

where the operator acts
Implemented
Dashboard
The control tower: the live stream evaluated snapshot by snapshot, the approval rate against its expected range, transaction volume behind that rate, a prioritized incident queue and the diagnosis workspace with its full evidence trail.
Channel
A real Slack webhook. Every supported incident carrying a real catalog action — not the monitoring fallback — sends one message to the operations channel: headline, operational evidence and the incident id, marked simulation only. An alert that fired on statistical noise would stop being an alert.
Prioritization
Incidents are ranked by the product of impact, scope, persistence, confidence and merchant criticality, with impact measured relative to the largest incident in the batch. Every component is exposed alongside the score, so the ranking can be inspected rather than trusted.
Stack
React + authored CSS · SSE from FastAPI for the stream · REST for queries and injection.
Verification
Delivery is confirmed, not assumed: the interface animates the channel alert only after Slack acknowledges it, and an incident open for minutes sends exactly one message. Measured end to end: 12–25 s from an injected signal to a delivered alert.
Hard cases

What the architecture is built to survive

An unrehearsed incident

An operator picks dimensions, magnitude and duration, and fires. The system detects, localizes and explains with no human intervention.

The deterministic localizer is what makes this work on a combination never seen before: it does not guess dimension by dimension, it tests complete hypotheses and keeps the one that explains what was observed.

Two incidents at once

Residualization lets the localizer return more than one cause. The stopping criterion is explicit: when adding a second cause does not significantly improve the explanation, there is only one.

They are shown separated and ranked by money at risk, instead of merged into a single outage that hides one of the two failures.

An unavailable dependency

The hot path reads the in-memory ring buffer, never the database, and every external call carries a timeout. The system runs end to end with PostgreSQL down.

If the language model is unavailable, deterministic templates render the same diagnosis from the same evidence. Wording degrades; operational truth does not.

Signal that is only noise

A low-volume slice can swing several points without meaning anything. The binomial detector weighs volume, the Wilson interval bounds the claim, and the classifier withholds a verdict when evidence is thin.

In that state the system recommends monitoring, attaches no cost figure and sends nothing to the operations channel.

Division of labour

Why the intelligence is deterministic

The two halves of the system answer different questions, and the boundary between them is the design:

Deterministic — the computation

Detection, localization, classification, cost and action selection. Auditable, reproducible, and it generalizes to slices never seen. This is the part that has to be correct under pressure, which is exactly why it does not depend on a model.

The model — the understanding

It interprets the resolved result against the business rules, phrases it for two audiences and answers questions about the evidence. The model produces the understanding, never the number.

Prior art

The problem has a name and a literature: multi-dimensional root cause localization (Adtributor, HotSpot, Squeeze, RiskLoc). Greedy drill-down is essentially Adtributor, and it assumes the cause lives in a single dimension — it fails on a cross-dimensional combination. Squeeze is the closer basis here because conversion is a derived measure, a ratio rather than a sum, so localization runs over attempts and approvals separately.

Trust contract

What every diagnosis carries

A diagnosis nobody can audit is worth nothing in payment operations. Each incident is emitted with the evidence needed to challenge it:

Evidence

Observed window and contextual reference. Sample size and approval delta in percentage points. Affected slice and the healthy controls that bound it. Dominant decline code and issuer-level evidence.

Limits

Primary hypothesis, competing alternatives and missing data. Confidence level and estimated financial impact with its assumptions stated. Lifecycle is explicit: observing → validating → diagnosing → detected / insufficient evidence → resolved.

With more time

What we would build next

Historical context per merchant and country
The engine compares against a seasonal baseline, but it does not yet know that a given merchant has failed three times this month. Feeding recurrence into the priority score would move the product from reporting to anticipating.
Segmented stream for the view filter
The view filter narrows KPIs and the incident queue by cube dimension, while the charts stay global because the stream ticker is not segmented. Segmenting it would let an operator watch a single provider in isolation, end to end.
Threshold calibration against production traffic
The detector thresholds are calibrated against the synthetic world and validated over 90 healthy windows. That is calibration evidence for this dataset, not a production false-positive guarantee; real traffic would move them.
Remediation with governed approval
Every action is simulation-only today. Executing one would require an approval trail, a rollback path and a policy the merchant signs off on — deliberately out of scope.
